# 共有索引、保存、保守の比較

次の 3 つの変更（64b8fe5）について、変更前後を比較した記録です。

- 全文検索を、ノートごとの索引から共有転置索引（形式 v2）に変えた
- リビジョンの本文と完全な版履歴を、1 つの不変オブジェクトにまとめた
- 保守 alarm で、チェックポイントと索引を交互に進めるようにした

変更前は main の `2e115d6d6b1b0b24ec2ee5f2bcd64ae65f6ce5df` です。

## 測定条件と再現方法

2026-10-06 に、Node 24 と公式の Vitest Workers 統合で、ローカルの workerd、SQLite DO、R2 の binding を使って測定しました。
同じ[測定ハーネス](../../test/performance/shared.test.ts)を変更前の隔離した worktree にコピーし、ソースに差分がないことを確認してから、変更前、変更後の順に実行しました。
ほかのテストとは並行して実行していません。
binding の計測用 proxy は固定し、ジャーナルのキャッシュの寿命を変えないようにしています。

R2 の操作ごとに、人工的に 2ms の遅延を加えています。
遠隔の R2 の遅延、同じキーへの書き込み頻度の制限、課金、Workers の CPU 上限は測っていません。
GET の回数はコードが発行する binding の操作の数で、R2 の課金の見積もりではありません。
5 回の試行の p95 は最大値と同じで、本番の SLO として使える統計ではありません。

```sh
PERF_LABEL=after pnpm test:performance -- test/performance/shared.test.ts
# 変更前：別の checkout の旧ソースに、同じハーネスと performance の設定をコピーして実行する
PERF_LABEL=before pnpm test:performance -- test/performance/shared.test.ts
```

すべてのサンプル、alarm ごとの進捗、SQLite のサイズは、[変更前](shared-index-before.json)と[変更後](shared-index-after.json)の JSON にあります。

## 検索

32、128、512 ノートのデータには、日本語、英語、識別子が混在しています。
クエリは 3 種類で、希少語は 1 ノートに、共通フレーズはすべてのノートに現れ、不一致の語はどのノートにも現れません。
limit は 10 です。
表の GET と LIST は、5 回の試行の合計を 5 で割った、1 検索あたりの回数です。
検索をまたいで再利用するキャッシュはなく、1 回の検索の中でのページのキャッシュは最大 16 ページです。

| 32、共通フレーズ | 33 → 15 | 1 → 0 | 104 → 49 | 105 → 49 |
| 32、不一致 | 33 → 3 | 1 → 0 | 104 → 9 | 107 → 10 |

変更後は該当する語の共有ページだけを読むので、検索のたびに全ノートの索引を GET する処理がなくなりました。
ただし、正確な BM25 の文書頻度の集計と順位付けのために、該当する投稿は複数回走査します。
そのため、共通語での CPU と GET の数は該当する文書数に比例し、本文ハッシュで無効になる上位候補が多い場合は追加の走査も必要です。
フォルダで絞り込んでも、BM25 の統計は Vault 全体のものを使います。
旧形式の索引を検索している移行中の間は、全件の走査が残ります。

## 正本の保存と復元

ケースは次のとおりです。
本文は短く非圧縮で、`new_edits=false` で書き込みます。
alarm は止めて、応答までの保存だけを測っています。

- **normal**：新しい文書 1 件のリクエストを 20 回
- **bulk-burst**：25 件のリクエストを 4 回
- **initial**：128 件のリクエストを 1 回
- **concurrent-16**：16 件の PUT を同時に発行する（DO の中では直列に処理される）

| 操作 | GET 前→後 | PUT 前→後 | p50 ms 前→後 | p95 ms 前→後 |
|---|---:|---:|---:|---:|
| normal | 20 → 20 | 80 → 60 | 17 → 15 | 19 → 18 |
| bulk-burst | 4 → 4 | 208 → 108 | 193 → 113 | 198 → 115 |
| initial | 1 → 1 | 258 → 130 | 952 → 528 | 952 → 528 |
| concurrent-16 | 16 → 16 | 64 → 48 | 140 → 121 | 278 → 241 |

複数の文書を 1 つのコミットと head の CAS にまとめる処理は、変更前からありました。
この変更で新しく加えたのは、本文と完全な版履歴を 1 つの不変オブジェクトにまとめたことで、N 文書のバッチの PUT は 2N+2 回から N+2 回に減りました。

head の 429 を注入したケースは、どちらの版も既存の 250ms の再試行を通り、269ms から 267ms でした。
注入は計測用 proxy の手前で行うので、失敗した 1 回は PUT の数に含みません。
DO の管理行をすべて消した後の復元は、GET が 89 回から 88 回、時間が 291ms から 318ms で、この測定では復元は速くなっていません。
offline-catchup は 8 回の `_revs_diff` だけ（どちらも GET 8 回）を測ったもので、実際のオフライン同期全体の性能ではありません。

本文、ジャーナル、head の CAS が成功するまで応答は返しません。
16MiB のリクエスト、4MiB の文書、1000 件などの上限も変わっていません。
保存形式 v3 と旧形式の読み取り、旧版へ直接戻せない点は[保存、復元、移行](../r2-operations.md#ロールバック)を参照してください。

## 索引構築と保守のコスト

| 索引構築 | PUT 前→後 | 構築時間 ms 前→後 |
|---|---:|---:|
| 32 ノート | 34 → 43 | 126 → 156 |
| 128 ノート | 130 → 195 | 467 → 788 |
| 512 ノート | 514 → 884 | 1847 → 3785 |

共有木を copy-on-write で更新するので、検索時の読み取りが減る代わりに、索引構築では書き込みが増えます。
小さな更新は、32 パスまたは 256KiB を目安に manifest の差分にまとめますが、再構築での PUT の数と時間の増加は残ります。
不変ページの独立した PUT は最大 4 並列にしていますが、CPU や構築の総費用は改善していません。

128 ノートで、チェックポイントと索引の両方が終わるまで手動で alarm を進めた結果は次のとおりです。

- 索引が最初に進むまでの alarm の回数：14 → 2
- チェックポイントが完了するまでの alarm の回数：13 → 47
- 全体の時間：1469 → 1539ms

索引とチェックポイントを交互に進めるので、チェックポイントの完了は遅れますが、索引が待たされ続けることはなくなりました。
通常の alarm のスケジュールの待ち時間（25ms など）はこの手動の測定に含まれないので、本番での完了時間には換算できません。
変更後の索引の 1 段階は 16 パスと 50ms を目安に区切りますが、ページの統合や 1 パスの処理のために 50ms を超える alarm もあります。

## 測定していないこと

遠隔の R2、多くの文書に現れる語や巨大な単語位置の列、更新が収束しない場合、巨大な履歴、CPU 制限による実際の強制終了は測定していません。
1 ページ 512KiB は目標であり、1 つのノートの投稿がこれを超える場合は JSON を一度に解析するので、入力量に比例するメモリを使います。

遠隔の R2 で比較する場合は、期間を限った Worker、SQLite DO の namespace、正本用と派生索引用の R2 バケットに同じ合成データを入れ、リクエスト数、総バイト数、同じ head への書き込み間隔、p50 と p95 を記録してから資源を削除する、という方法が考えられます。
これには実際の資源の作成、利用料金、認証情報、削除の計画が必要で、まだ行っていません。
