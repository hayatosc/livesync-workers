# チェックポイントのバックグラウンド化

復元用のチェックポイントを、書き込みの応答の中で行う方式から、alarm による段階的なバックグラウンド処理に変えたとき（b6c1295）の比較です。
変更前は 7ffc94e で、2026-10-06 に同じマシンと同じハーネスで順に実行しました。

## 測定条件

公式の Vitest Workers 統合で、ローカルの workerd、SQLite DO、R2 の binding を使いました。
コンテンツ用バケットの各操作に、人工的に 2ms の待機を加えています。
本番 R2 の遅延、スループット、費用を測った結果ではありません。

測定したケースは次のとおりです。

- 通常の更新 20 回
- 初回同期（32 文書のバッチを 8 回）
- 同時の更新 20 件
- 圧縮済みの 512 版がある状態での更新 10 回
- 長期間オフラインだったクライアントの復帰（9 リクエスト）
- チェックポイントの境界（128 文書と 1024 文書は独立に 5 回、4096 文書は 3 回）

境界を再現するために、テストでは seq を直接設定しています。
索引の alarm は止め、チェックポイントは明示的に最後まで進めて（drain）、応答と保守の作業を分けて測っています。
全処理時間はこの drain を含みますが、実際の alarm の 25ms の待機やネットワークの待ち時間は含みません。
SQLite の最大サイズは約 2.4MB で、GiB 規模や本番の CPU 制限は検証していません。
試行回数が少ないので、p95 は参考値です。

## 応答時間

| ケース（単位 ms） | 応答 p50 変更前→後 | 応答 p95 変更前→後 | 全処理時間 変更前→後 |
|---|---:|---:|---:|
| 通常の更新 | 21→18 | 31→20 | 467→362 |
| 初回同期 | 248→240 | 269→243 | 2017→1919 |
| 短いオフラインからの復帰 | 3→4 | 4→4 | 28→30 |
| 同時の更新 20 件 | 224→196 | 408→351 | 429→368 |
| head の 429 を 1 回注入 | 324→271 | 324→271 | 324→271 |
| 圧縮後の新しい更新 | 46→17 | 53→33 | 467→187 |
| 長期オフラインからの復帰 | 44→33 | 45→87 | 360→373 |
| 境界 128 文書 | 59→18 | 64→20 | 59→78 |
| 境界 1024 文書 | 180→19 | 389→26 | 180→208 |
| 境界 4096 文書 | 613→21 | 681→23 | 613→775 |

チェックポイントを応答から外したことで、4096 文書の境界でも、通常どおり 4 回の PUT で応答します。
ただし全処理時間は 613ms から 775ms に、PUT の総数は 139 から 144 に増え、alarm は 137 回実行されています。
総作業量が減ったわけではありません。
長期オフラインからの復帰の p95 は 45ms から 87ms に悪化しており、旧版を参照するときのアーカイブの走査には改善の余地があります。

## R2 の操作数と SQLite のサイズ

| ケース | 応答中の R2 GET / PUT 変更前→後 | R2 GET / PUT の総数 変更前→後 | SQLite の最終サイズ（bytes） 変更前→後 |
|---|---:|---:|---:|
| 通常の更新 | 40 / 80→20 / 80 | 40 / 80→20 / 80 | 98304→126976 |
| 初回同期 | 16 / 528→8 / 528 | 16 / 528→8 / 528 | 237568→266240 |
| 短いオフラインからの復帰 | 8 / 0→8 / 0 | 8 / 0→8 / 0 | 98304→126976 |
| 同時の更新 20 件 | 40 / 80→20 / 80 | 40 / 80→20 / 80 | 98304→126976 |
| head の 429 を 1 回注入 | 7 / 8→1 / 5 | 7 / 8→1 / 5 | 90112→118784 |
| 圧縮後の新しい更新 | 100 / 40→13 / 40 | 100 / 40→13 / 40 | 94208→122880 |
| 長期オフラインからの復帰 | 113 / 0→81 / 0 | 113 / 0→81 / 0 | 94208→122880 |
| 境界 128 文書 | 2 / 14→1 / 4 | 2 / 14→1 / 19 | 135168→163840 |
| 境界 1024 文書 | 2 / 42→1 / 4 | 2 / 42→1 / 47 | 647168→675840 |
| 境界 4096 文書 | 2 / 139→1 / 4 | 2 / 139→1 / 144 | 2375680→2404352 |

境界のケースの R2 操作数と SQLite のサイズは、各サイズの 1 回目の試行の値です。
各試行の最大 SQLite サイズ、alarm の回数、再送の回数を含む完全な結果は、[変更前](checkpoint-before.json)と[変更後](checkpoint-after.json)の JSON にあります。

head の 429 を注入したケースでは、変更前はクライアントが同じ rev を再送し、変更後はサーバーが同じ条件つきの head 更新を再試行します。
1 回だけの障害での比較であり、制限が続く状況での性能を予測するものではありません。

## 再実行の方法

```sh
pnpm install --frozen-lockfile
PERF_LABEL=after pnpm test:performance -- test/performance/sync.test.ts
```

変更前の値は、7ffc94e の別の worktree に、現在の `vitest.performance.config.ts` と `test/performance/sync.test.ts` だけをコピーし、同じ lockfile の依存で実行して得ました。
変更前のライブラリのソースは変更していません。
比較するときは、ほかのテストや E2E を並行して実行しないでください。

## 測定していないこと

実際の Workers の CPU 制限、GiB 規模のデータ、実際の R2 での同一キーの書き込み制限、数時間にわたる連続した更新、実ユーザーの Vault は測定していません。
本番に近い測定には、一時的な Worker、SQLite DO の namespace、コンテンツ用と検索用の R2 バケットを用意し、課金と後片付けまで含めて計画する必要があります。
