# R2保存・運用・復元

## 保存の確定点

VaultごとにDOがHTTP操作とalarmを直列化します。リビジョンの不変本文を先にR2へ保存し、SQLiteにはR2参照とリビジョン木・勝者・変更フィード等を書きます。そのリクエストでの管理DB更新を復元用コミットに保存し、条件付きR2 head更新に成功してから応答・変更通知を返します。R2とSQLiteをまたぐトランザクションは仮定しません。

headは直前headのETag条件で更新します。読み取った管理状態よりR2 headが進んでいる場合も更新を拒否します。不変コミットは前コミットを参照し、bodyless祖先・削除・復元に必要なSQL操作を含みます。検索索引は正本に含めません。

```
content/v1/<encoded-owner>/<encoded-vaultId>/
  objects/<sha256>         リビジョンJSON・同期チェックポイント・バイナリ原本
  commits/<uuid>.json      不変の復元操作・前コミット参照
  head.json                唯一の現在の確定位置
search/ja-segmenter-nfkc-v1/<encoded-owner>/<encoded-vaultId>/
  state.json               active／building索引世代
  <generation>/<path>.json 派生の単語位置索引
```

このキー構造は整理用で、アクセス認可の代わりにはしません。外部R2キーを入力するAPIはありません。

## 障害と再試行

| 保存境界 | 再開時の状態 |
|---|---|
| 不変本文保存前／途中 | headは変更されず、更新は未確定 |
| 本文成功、コミット失敗 | 未使用本文が残ることがある。headからは到達不能 |
| コミット成功、head失敗 | 未使用コミットが残ることがある。旧headを復元 |
| head成功、応答またはSQLite確定前に障害 | 新headから管理DBを再構築。更新は失われない |
| DO管理DB消失 | headのコミット列を再生し、索引を再構築 |

例外時と次のアクセス時にR2 headを照合します。SQLiteにも再構築可能な適用済みheadマーカーを保存し、DOインスタンスが存続したまま管理DBが消えても再生します。成功応答済み更新だけでなく、head成功後に応答を失った更新も復元対象です。その場合、通常編集の再送で409となることがあり、クライアントは現在のリビジョンを再取得します。`new_edits=false`は同一リビジョンの再送が冪等です。MCPの上書き・追記では前本文ハッシュを照合し、同時更新を拒否します。追記の応答喪失後の新しい操作には重複排除IDがないため、再読取して成功の有無を確認してください。

`_compact`はR2方式で版を破壊しません。履歴と削除記録は正本に残します。`purge`によるDB削除もコミットに残り、復元時に以前の文書が再出現しません。これは完全消去とは異なり、履歴保持です。

## 既存SQLiteデータの明示移行

本セッションではテスト用データのみ移行しました。実データには適用していません。

1. 書込を停止し、既存の設定・Worker版・元DOとR2を退避します。移行後に新Vaultを作成する操作を先に行わないでください。空の作成コミットも移行先が既存であると判定されます。
2. 同じ所有範囲で新しい不変`vaultId`を決めます。旧DO名は`${tenantId}:${databaseName}`、新DO名は`vaultObjectName({tenantId,vaultId,databaseName})`です。
3. 管理用の、当該namespaceバインディングにアクセスできるホストコードから旧DOへ、`POST https://livesync-db/internal/migrate-r2`を送ります。ヘッダー`X-LiveSync-Internal`は既存内部secret、JSON本文は`{"targetVaultId":"primary"}`です。この内部URLは公開LiveSync経由では呼べません。
4. 移行処理は旧DOの排他区間で、本文・リビジョン管理・ローカル同期チェックポイントを移行先R2へコピーします。移行先headが既にある場合は409で拒否します。元DOは変更しません。応答のcommitを記録します。
5. 新DOでheadからの復元を確認し、文書数、変更seq、複数リビジョン、チャンク内容、添付、削除、チェックポイントを比較します。`test/workers/migration.test.ts`は実Workers／SQLite／R2でこの手順を検証しています。
6. 検証後に接続先を新DOへ切り替え、旧DOを凍結したまま保持します。接続名と表示名を変更しても不変IDは変えません。検索索引の再構築が完了してから検索を確認します。

これは運用手順であり、本番の実行や臨時管理Workerのdeployを承認したものではありません。

## ロールバック

切替前、または新Vaultに書込がない段階では、保存した旧Worker／設定と未変更の旧DOに接続を戻せます。旧DO・旧索引を削除しないでください。

新Vaultに書込後は、旧DOへ戻るだけでは新更新を失います。書込停止、R2正本の退避、新Vaultからの通常LiveSyncレプリケーション／Vaultファイル復元、差分検証を先に行い、更新を引き継いでから切り替えます。DO内のR2ポインタを旧Workerで直接開くことはできません。履歴も必要ならR2コミット列と本文を保持し、新方式で復元してから互換APIで取り出します。

## 未使用オブジェクトの回収

内部APIの`POST /internal/op`へ`{"op":"contentGc"}`を送ると、Vaultの排他区間で`R2Journal.collectGarbage()`を呼び出します。既存内部secretが必要で、既定はdry runです。headから到達できる全コミット・本文・バイナリ原本を保持し、既定24時間より古い到達不能オブジェクトだけを候補にします。実削除は`{"op":"contentGc","execute":true}`を指定します。ライブラリから直接呼ぶ場合もVaultの排他ロックを保持した状態で実行します。実削除直前にもhead変化を検出します。履歴保持対象は回収しません。R2ライフサイクルで`objects/`や`commits/`を一律削除しないでください。

## 容量・性能と検証範囲

本文をSQLiteへ退避して容量制限を隠す方式は使いません。管理メタデータは1VaultのSQLite DOに収まる必要があります。リビジョン／索引生成時のWorkersメモリとCPU制限は残ります。

検索は文書単位の転置索引をR2から順に読み、Vault全本文を一括保持しません。ただしR2読取数は文書数に比例し、大Vaultの遅延・費用は未ベンチマークです。現在のR2コミット再生と明示移行は全コミット／全管理操作を読むため、巨大な履歴の復元時間・メモリには限界があります。ページ付きチェックポイント／増分再生の運用最適化はまだありません。大量データでの本番適性をこのテスト結果から主張しません。

テストはローカルworkerdの本物のWorkers／DO／R2バインディングです。CPU制限による実強制終了、ネットワーク断、本番R2障害、本番負荷、大規模な本番クライアント同期は未検証です。実Obsidianと公式CLIの隔離E2Eは[テスト文書](testing.md)の通り成功しています。保存境界での注入障害、成功head後の応答喪失、管理DB消去後の再生は検証しています。

## 実DO内部のVault識別

実workerdのDO内部では`ctx.id.name`が取得できない場合があります。認証済みWorkerとVaultClientは、`X-LiveSync-Vault-Ref`へ`encodeURIComponent(JSON.stringify(ref))`、既存`X-LiveSync-Internal`へ内部secretを設定します。DOはsecret・実DO ID一致・ホストpolicyを確認して識別情報だけをDO KVへ保持します。R2ホストの識別不能は失敗として返し、本文のSQLite fallbackには入りません。初回の直接内部API／旧源移行呼出も、識別がまだ保持されていなければこの信頼済み参照が必要です。認証前の外部ヘッダーはWorkerが上書きします。
