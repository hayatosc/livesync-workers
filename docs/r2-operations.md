# 保存、復元、移行

## 保存の確定点

Vault ごとの DO が、HTTP の操作と alarm を直列に処理します。
1 回の書き込みは次の順で確定します。

1. リビジョンの不変な本文と完全な版履歴を、形式 v3 の 1 つのオブジェクトとして R2 に保存する。
2. SQLite に、R2 への参照、リビジョン木、勝者、変更フィードなどを書く。
3. そのリクエストで行った管理 DB の更新を、復元用のコミットとして R2 に保存する。
4. R2 の head を条件付きで更新する。
5. 成功してから、応答と変更通知を返す。

R2 と SQLite をまたぐトランザクションは前提にしていません。
head が確定するまでは更新は未確定で、確定した後に障害が起きても R2 から管理 DB を再構築できます。

head は、直前の head の ETag を条件にして更新します（CAS）。
DO が読み込んだ管理状態より R2 の head が進んでいる場合も、更新を拒否します。
不変コミットは前のコミットを参照し、本文を持たない祖先、削除、復元に必要な SQL 操作を含みます。
検索索引は正本に含めません。

## R2 のキー構成

```
content/v1/<encoded-owner>/<encoded-vaultId>/
  objects/<sha256>         リビジョンの JSON、履歴、アーカイブ、復元用ページ、バイナリの原本
  commits/<uuid>.json      不変の復元操作と、前のコミットへの参照
  head.json                現在の確定位置（唯一）
search/ja-segmenter-nfkc-v1/<encoded-owner>/<encoded-vaultId>/
  state.json               active と building の索引世代
  <generation>/manifest.json      CAS で確定する派生索引の根、統計、小さな変更
  <generation>/pages/<uuid>.json  不変の文書ページと単語位置の共有ページ
  <generation>/notes/<uuid>.json  原文ハイライト用の派生テキスト
```

このキー構成は整理のためのもので、アクセスの認可には使いません。
外部から R2 のキーを指定できる API はありません。

## 障害と再試行

| 障害が起きた時点 | 再開したときの状態 |
|---|---|
| 不変本文の保存前または保存中 | head は変わらず、更新は未確定 |
| 本文の保存後、コミットの保存に失敗 | 使われない本文が残ることがある。head からは到達しない |
| コミットの保存後、head の更新に失敗 | 使われないコミットが残ることがある。旧 head の状態に戻す |
| head の更新後、応答または SQLite の確定前 | 新しい head から管理 DB を再構築する。更新は失われない |
| DO の管理 DB が消えた | 最新のチェックポイントと、その後のコミットを再生する。索引は再構築する |

例外が起きたときと、次にアクセスがあったときに、R2 の head と照合します。
alarm の継続処理では同じ DO が適用済みの head を再利用し、確定時の CAS で外部からの更新を検出します。
SQLite にも適用済み head の目印を保存しているので、DO のインスタンスが残ったまま管理 DB だけが消えた場合も再生できます。

R2 の PUT は、明示的な 429 と 503 に限り、250、500、1000ms の間隔で最大 3 回再試行します。
同じキーへの書き込み頻度は [R2 の公式の制限](https://developers.cloudflare.com/r2/platform/limits/)に従います。
1 リクエストのバッチには複数の文書を含められるので、「1 文書あたり毎秒 1 回」という上限にはなりません。

head の更新が成功した後に応答だけが失われた更新も、復元の対象です。
この場合、クライアントが通常の編集として再送すると 409 になることがあるので、クライアントは現在のリビジョンを取得し直します。
`new_edits=false` による同じリビジョンの再送は冪等です。

## 圧縮とチェックポイント

`POST /_compact` は HTTP 202 `{ok:true,pending:true}` を返し、alarm による段階的な処理を予約します。
現在の競合している葉と墓標は SQLite に残し、葉でないリビジョンと、その検索管理用のメタデータを R2 のアーカイブに移します。
変更記録は、文書ごとの最新の seq にまとめます。

索引は各 ID の現在の勝者を処理するので、未処理の更新は失われず、pending の行も保持します。
旧版の読み取り、`_revs_diff`、祖先を指定した `open_revs` と `latest=true` は、アーカイブを参照します。
seq は削除や圧縮の後も単調に増え、長期間オフラインだったクライアントには、その時点の葉と削除状態を返します。

チェックポイントは、4096 更新 seq ごと、または容量の余裕がなくなる前に予約します。
通常の書き込みの応答は、本文、コミット、head の CAS が確定した時点で返し、チェックポイントの完了は待ちません。
現存するメタデータの正本キャッシュと同期処理は、引き続き SQLite DO が担います。

alarm 1 回あたりの処理は、次のどちらかです。

- 葉でないリビジョンを最大 32 行、アーカイブに移す。
- 管理 DB を走査して、最大 128 行を不変の R2 ページに書き出す。

ページは 128 ページごとに参照カタログでまとめ、処理位置（カーソル）は SQLite に保存します。
走査中に更新や削除された行は、SQL トリガーで主キーを記録しておき、現在の状態の UPSERT または DELETE のページとして後から順に適用します。
記録された未反映のキーがなくなった排他区間でだけ、現在の head を CAS で更新し、復元可能なスナップショットとして公開します。
圧縮済みの seq は処理を始めた時点の値なので、開始後の更新を圧縮済みと誤認することはありません。

ページの保存に失敗したときは、同じカーソルから再試行します。
DO が再起動したときは、保存済みのカーソルから続けます。
正本の更新と食い違ったときや失敗したときは、R2 から復元してやり直します。
未完了のチェックポイントのページは、GC の保護対象に含めます。
アーカイブは 32 行ずつ移しますが、ページは最大 128 版ごとにまとめます。
古い R2 のコミット、版、削除記録は保持します。

段階的に処理することで応答の待ち時間は短くなりますが、alarm の回数や未反映ページの処理など、総コストは増える場合があります。
高頻度の更新が続いて未反映のキーが増えている間は、スナップショットの公開が遅れます。
進み具合は、`vaultStatus` または `indexStatus` の `checkpointProgress`（phase、開始 seq、未反映の件数）で確認できます。
ローカルでの測定結果は[性能測定の記録](benchmarks/checkpoint.md)にあります。

`purge` による DB の削除もコミットとして残るので、復元しても以前の文書は再び現れません。
ただしこれは履歴を残した削除であり、データの完全な消去ではありません。

## 既存SQLiteデータの移行

この手順はテスト用のデータでのみ検証しており、実データにはまだ適用していません。

1. 書き込みを止め、現在の設定、Worker の版、元の DO、R2 を退避する。
   移行より先に新しい Vault を作成しないこと。空の作成コミットがあるだけでも、移行先は既存と判定される。
2. 同じ所有範囲で、新しい不変の `vaultId` を決める。
   旧 DO の名前は `${tenantId}:${databaseName}`、新 DO の名前は `vaultObjectName({tenantId,vaultId,databaseName})` になる。
3. その namespace の binding にアクセスできる管理用のホストコードから、旧 DO に `POST https://livesync-db/internal/migrate-r2` を送る。
   ヘッダー `X-LiveSync-Internal` に内部 secret を、本文に `{"targetVaultId":"primary"}` のような JSON を入れる。
   この内部 URL は、公開している LiveSync の API からは呼べない。
4. 旧 DO は排他区間の中で、本文、リビジョンの管理情報、ローカル同期のチェックポイントを移行先の R2 にコピーする。
   移行先に head がすでにある場合は 409 で拒否する。元の DO は変更しない。応答に含まれるコミットを記録しておく。
5. 新しい DO で head から復元できることを確認し、文書数、変更 seq、複数リビジョン、チャンクの内容、添付、削除、チェックポイントを比較する。
   `test/workers/migration.test.ts` は、実際の Workers、SQLite、R2 でこの手順を検証している。
6. 検証できたら接続先を新しい DO に切り替え、旧 DO は凍結したまま残す。
   接続名や表示名を変えても、不変 ID は変えない。検索は、索引の再構築が終わってから確認する。

この節は手順の説明であり、本番での実行や、移行用の Worker の deploy を前提にしたものではありません。

## ロールバック

切り替える前か、新しい Vault にまだ書き込みがない段階なら、保存しておいた旧 Worker と設定、変更していない旧 DO に接続を戻せます。
判断が終わるまで、旧 DO と旧索引は削除しないでください。

新しい Vault に書き込んだ後は、旧 DO に戻すだけでは新しい更新が失われます。
書き込みを止め、R2 の正本を退避し、新しい Vault から通常の LiveSync レプリケーションか Vault のファイルで更新を取り出し、差分を確認してから切り替えます。

旧版の Worker は、DO の中の R2 ポインタを直接開けません。
現在の書き込みとチェックポイントはコミット形式 v3 で、形式 v1 と v2 は読み取りだけできます。
本文と履歴は、同じオブジェクトの `part:body` と `part:history` への参照です。
適用済み head の目印には `r2_applied_head_v3` というキーを使い、旧版が既存のキャッシュだけを見て v3 の head を処理済みと誤認しないようにしています。

形式 v3 に対応していない版（7ffc94e 以前）は、新しく復元しようとすると未対応の形式を検出して失敗します。
そのような版に戻すときは、先に現在の版で復元し、互換 API で差分を取り出してください。
旧 SQLite のキャッシュが残っていることを、互換性の根拠にはできません。
履歴も必要なら、R2 のコミット列と本文を保持したまま現在の版で復元し、互換 API で取り出します。

## 未使用オブジェクトの回収

内部 API の `POST /internal/op` に `{"op":"contentGc"}` を送ると、Vault の排他区間で `R2Journal.collectGarbage()` を実行します。
内部 secret が必要で、既定では削除せずに候補を返すだけ（dry run）です。
実際に削除するには `{"op":"contentGc","execute":true}` を送ります。

head から到達できるコミット、本文、バイナリの原本はすべて保持し、到達できず既定で 24 時間より古いオブジェクトだけを削除の候補にします。
未完了のチェックポイントのページとカタログも保護します。
削除する直前にも head が変わっていないかを確認します。

ライブラリから直接呼ぶ場合も、Vault の排他ロックを持った状態で実行してください。
R2 のライフサイクルルールで `objects/` や `commits/` をまとめて削除しないでください。

## 容量と性能の制約

本文を SQLite に戻して容量の制限を回避する方式は採っていません。
現存する文書、競合している葉、ローカル同期の進捗、索引の管理情報は、1 Vault の SQLite DO に収まる必要があります。
[公式の上限](https://developers.cloudflare.com/durable-objects/platform/limits/)は、1 つの DO あたり Paid プランで 10GB、Free プランで 1GB です。

`vaultStatus` と `indexStatus` の `capacity` は、SQL API の `databaseSize`、設定した上限、余裕、書き込みの可否を返します。
既定は `SQLITE_MAX_BYTES=900000000` と `SQLITE_HEADROOM_BYTES=100000000` です。
使用量が 800MB 以上になるとバックグラウンドの圧縮を予約し、完了するまでも、容量を増やす更新は HTTP 507 `SQLITE_CAPACITY` で拒否します。
圧縮が終わったら再試行し、改善しなければ拒否を続けます。
読み取りと明示的な圧縮は続けられます。

Paid プランでは、プランを確認したうえで上限を 9500000000 以下に設定でき、余裕は 500000000 程度を推奨します。
ライブラリを組み込む場合は、`VaultBindings.sqliteMaxBytes` と `sqliteHeadroomBytes` で設定します。
上限の近くで巨大なリクエストを 1 つ受けた場合の `SQLITE_FULL` や CPU 制限までは、完全には防げません。

検索は形式 v2 の共有転置索引から該当する単語のページだけを読み、全ノートの索引を GET したり LIST したりはしません。
出現の少ない語や一致しない語の読み取りは木の深さで決まります。
一方、多くのノートに現れる語は該当文書数に比例し、正確な BM25 の統計と順位付けのために複数回走査します。
無効な候補が多い場合も走査は増えます。
本番での遅延と費用は測定していません。

通常の復旧はチェックポイント以降の再生に限られ、本文を一括でメモリに持つことはありません。
ただし、チェックポイントのない旧形式の履歴、GC での全履歴の走査、深い版のアーカイブ参照、明示的な移行には、履歴や現存メタデータの量に比例する費用がかかります。

テストはローカルの workerd で、本物の Workers、DO、R2 の binding を使っています。
CPU 制限による実際の強制終了、ネットワークの切断、本番 R2 の障害、本番の負荷、大規模なクライアント同期は検証していません。
保存の各境界での障害注入、head 更新後の応答の喪失、管理 DB を消した後の再生は検証済みです。
実 Obsidian と公式 CLI での E2E については[テストと CI](testing.md)を参照してください。

## DO の中での Vault の識別

実際の workerd では、DO の中で `ctx.id.name` を取得できない場合があります。
そこで、認証済みの Worker と Vault クライアントは、DO へのリクエストに次のヘッダーをつけます。

- `X-LiveSync-Vault-Ref`：`encodeURIComponent(JSON.stringify(ref))`
- `X-LiveSync-Internal`：内部 secret

DO は、secret、実際の DO ID との一致、ホストのポリシーを確認してから、識別情報だけを DO の KV に保存します。
R2 を使うホストで Vault を識別できない場合はエラーにし、本文を SQLite に保存する経路には入りません。
識別情報がまだ保存されていない DO に内部 API や移行を直接呼ぶ場合も、この信頼済みの参照が必要です。
認証前の外部リクエストに含まれるこれらのヘッダーは、Worker が上書きします。

## 保守 alarm と派生索引

alarm は、チェックポイントの 1 段階と索引の 1 段階を交互に進めます。
一方が失敗し続けても、もう一方の処理が止まることはありません。

索引の 1 段階は最大 16 パスで、パスの間で 50ms を目安に次の alarm へ延期します。
1 パスの処理を途中で打ち切る期限ではありません。
延期は失敗の回数に数えず、pending として保存します。

欠けていたチャンクが届いたときは、再試行の上限に達したノートも含めて、カーソルで全件を確認し直します。
カーソルは実際に試したパスまでしか進めません。
確認の途中でさらにチャンクが届いた場合は、次の全件確認を予約します。
alarm が続けて実行され、各パスが有限時間で終わり、入力が収束するという条件のもとで、索引は完了します。
未反映の更新が増え続ける状況では、チェックポイントが完了するまでの時間に上限はありません。

索引の版 4 への更新では、索引を再構築します。
形式 v1 の active 世代は、新しい世代が完成するまで検索に使え、再構築中に保存が失敗しても切り替えません。

形式 v2 は、不変の文書木と、単語およびパスの木、CAS で更新する manifest から成ります。
小さな変更は、32 パスまたは 256KiB を目安に木へ統合し、それまでは上限のある manifest の差分として持ちます。
木の葉は 64 行または 512KiB、分岐数は 32、ページのキャッシュは最大 16 ページを目安にしています。
1 つのノートが非常に大きい場合は 512KiB を超えることがあり、そのページの JSON は一度に解析します（ストリーム解析はしません）。
索引対象のノートは 100 万 UTF-16 コード単位まで、という制限とリクエストの上限は残り、本番の CPU やメモリへの適合を保証するものではありません。

独立した不変ページの PUT は最大 4 並列で行い、失敗したときも、開始したすべての保存が終わってから失敗を返します。
writer の upsert と delete は仮の確定であり、close が成功するまでは完了として扱いません。
close が失敗したときは、試したすべてのパス（削除を含む）を再試行します。

全文検索のクエリは、最大 4096 UTF-8 バイト、32 種類の単語までです。
結果の件数は、ライブラリでは 1 から 1000、MCP では 1 から 50 です。

派生索引の `collectGarbage` も、既定では dry run で、猶予は 24 時間です。
直接呼ぶ場合は Vault の writer と同じ排他ロックの中で実行し、進行中の読み取りより十分に長い猶予を設定してください。
active と building の根、差分、原文への参照、旧 active 世代の全体を保護します。
これはコンテンツの正本の GC とは別のもので、公開している MCP の操作からは呼べません。
