# R2保存・運用・復元

## 保存の確定点

VaultごとにDOがHTTP操作とalarmを直列化します。リビジョンの不変本文と完全な版履歴を同じ形式v3オブジェクトへ先にR2保存し、SQLiteにはR2参照とリビジョン木・勝者・変更フィード等を書きます。そのリクエストでの管理DB更新を復元用コミットに保存し、条件付きR2 head更新に成功してから応答・変更通知を返します。R2とSQLiteをまたぐトランザクションは仮定しません。

headは直前headのETag条件で更新します。読み取った管理状態よりR2 headが進んでいる場合も更新を拒否します。不変コミットは前コミットを参照し、bodyless祖先・削除・復元に必要なSQL操作を含みます。検索索引は正本に含めません。

```
content/v1/<encoded-owner>/<encoded-vaultId>/
  objects/<sha256>         リビジョンJSON・履歴・アーカイブ・復元ページ・バイナリ原本
  commits/<uuid>.json      不変の復元操作・前コミット参照
  head.json                唯一の現在の確定位置
search/ja-segmenter-nfkc-v1/<encoded-owner>/<encoded-vaultId>/
  state.json               active／building索引世代
  <generation>/manifest.json  CASで確定する派生索引の根・統計・小変更
  <generation>/pages/<uuid>.json  不変の文書／単語位置共有ページ
  <generation>/notes/<uuid>.json  原文ハイライト用の派生テキスト
```

このキー構造は整理用で、アクセス認可の代わりにはしません。外部R2キーを入力するAPIはありません。

## 障害と再試行

| 保存境界 | 再開時の状態 |
|---|---|
| 不変本文保存前／途中 | headは変更されず、更新は未確定 |
| 本文成功、コミット失敗 | 未使用本文が残ることがある。headからは到達不能 |
| コミット成功、head失敗 | 未使用コミットが残ることがある。旧headを復元 |
| head成功、応答またはSQLite確定前に障害 | 新headから管理DBを再構築。更新は失われない |
| DO管理DB消失 | 最新のページ化チェックポイントとその後のコミットを再生し、索引を再構築 |

例外時と次のアクセス時にR2 headを照合します。alarm継続では同じDOの適用済みheadを再利用し、確定時CASで外部更新を検出します。R2 PUTの明示429／503のみ250・500・1000msで最大3回再試行します。同一head名への書込上限は[公式R2制限](https://developers.cloudflare.com/r2/platform/limits/)に従いますが、1リクエストのバッチには複数文書を含められるため1文書／秒の上限とは扱いません。SQLiteにも再構築可能な適用済みheadマーカーを保存し、DOインスタンスが存続したまま管理DBが消えても再生します。成功応答済み更新だけでなく、head成功後に応答を失った更新も復元対象です。その場合、通常編集の再送で409となることがあり、クライアントは現在のリビジョンを再取得します。`new_edits=false`は同一リビジョンの再送が冪等です。MCPの上書き・追記では前本文ハッシュを照合し、同時更新を拒否します。追記の応答喪失後の新しい操作には重複排除IDがないため、再読取して成功の有無を確認してください。

`POST /_compact`はHTTP 202 `{ok:true,pending:true}`を返し、alarmによる段階的処理を予約します。現在の競合葉・墓標をSQLiteに残し、非葉リビジョンとその検索管理メタデータをR2アーカイブへ退避します。変更記録は文書ごとの最新seqに集約します。索引は各IDの現在の勝者を処理するため未処理更新も失われず、pending行は保持します。旧版読取・`_revs_diff`・祖先指定の`open_revs&latest=true`はアーカイブを参照します。seqは削除／圧縮後も単調増加し、長期オフラインのクライアントには現時点の葉と削除状態を返します。

4096更新seqごと、または容量余裕がなくなる前にチェックポイントを予約します。通常書込の応答は本文・コミット・head CASの確定後に返し、チェックポイント完了を待ちません。現存メタデータの正本キャッシュ・同期処理は引き続きSQLite DOです。

alarmごとに非葉リビジョンを最大32行退避するか、管理DBを最大128行の不変R2ページへ走査します。128ページ単位の参照カタログで保持し、処理カーソルはSQLiteへ保存します。走査中の更新・削除はSQLトリガーで主キーを記録し、現状態のUPSERT／DELETEページを後から順序付きで適用します。dirtyキーがなくなった排他区間でだけ現在のheadをCAS更新し、復元可能なスナップショットを公開します。更新seqは単調増加し、圧縮済みseqは処理開始時点の水位です。開始後の更新を圧縮済みと誤認しません。

通常アクセスでは適用済みhead以降だけを再生し、管理DB消失時には最新チェックポイントから復元します。ページ保存失敗は同じカーソルから再試行します。DO再起動では保存済みカーソルから継続し、正本更新の不一致・失敗ではR2から復元して安全に開始し直します。未完了のページはGCの保護ルートに含めます。R2リビジョンアーカイブは32行ずつ退避しても最大128版のページへまとめます。古いR2コミット・版・削除記録は保持します。

段階処理は応答待ち時間を減らす一方、alarm回数・dirtyページ等の総コストを増やす場合があります。継続的な高頻度更新でdirtyキーが増える間は公開が遅れます。`vaultStatus`／`indexStatus`の`checkpointProgress`でphase・開始seq・dirty件数を確認できます。[性能測定](performance.md)はローカル結果と制約を記載しています。

`purge`によるDB削除もコミットに残り、復元時に以前の文書が再出現しません。これは完全消去とは異なり、履歴保持です。

## 既存SQLiteデータの明示移行

本セッションではテスト用データのみ移行しました。実データには適用していません。

1. 書込を停止し、既存の設定・Worker版・元DOとR2を退避します。移行後に新Vaultを作成する操作を先に行わないでください。空の作成コミットも移行先が既存であると判定されます。
2. 同じ所有範囲で新しい不変`vaultId`を決めます。旧DO名は`${tenantId}:${databaseName}`、新DO名は`vaultObjectName({tenantId,vaultId,databaseName})`です。
3. 管理用の、当該namespaceバインディングにアクセスできるホストコードから旧DOへ、`POST https://livesync-db/internal/migrate-r2`を送ります。ヘッダー`X-LiveSync-Internal`は既存内部secret、JSON本文は`{"targetVaultId":"primary"}`です。この内部URLは公開LiveSync経由では呼べません。
4. 移行処理は旧DOの排他区間で、本文・リビジョン管理・ローカル同期チェックポイントを移行先R2へコピーします。移行先headが既にある場合は409で拒否します。元DOは変更しません。応答のcommitを記録します。
5. 新DOでheadからの復元を確認し、文書数、変更seq、複数リビジョン、チャンク内容、添付、削除、チェックポイントを比較します。`test/workers/migration.test.ts`は実Workers／SQLite／R2でこの手順を検証しています。
6. 検証後に接続先を新DOへ切り替え、旧DOを凍結したまま保持します。接続名と表示名を変更しても不変IDは変えません。検索索引の再構築が完了してから検索を確認します。

これは運用手順であり、本番の実行や臨時管理Workerのdeployを承認したものではありません。

## ロールバック

切替前、または新Vaultに書込がない段階では、保存した旧Worker／設定と未変更の旧DOに接続を戻せます。旧DO・旧索引を削除しないでください。

新Vaultに書込後は、旧DOへ戻るだけでは新更新を失います。書込停止、R2正本の退避、新Vaultからの通常LiveSyncレプリケーション／Vaultファイル復元、差分検証を先に行い、更新を引き継いでから切り替えます。DO内のR2ポインタを旧Workerで直接開くことはできません。現在の書込・チェックポイントはコミット形式v3で、形式v1／v2は読取可能です。本文と履歴は同じオブジェクトへの`part:body`／`part:history`参照になります。新しい適用済みheadキー`r2_applied_head_v3`を使い、旧バイナリが既存キャッシュだけでv3 headを処理済みと誤認することを防ぎます。旧版へ戻すと未対応コミットで失敗するため、現在版で復元して互換APIから取り出す手順が必要です。前版7ffc94eの新規復元は未対応形式を検出して失敗します。旧SQLiteキャッシュが残ることを互換性の根拠にしないでください。チェックポイントと履歴ポインタを理解しない前版へのロールバックも、現在版で復元・互換APIで差分を取り出してから行います。履歴も必要ならR2コミット列と本文を保持し、新方式で復元してから互換APIで取り出します。

## 未使用オブジェクトの回収

内部APIの`POST /internal/op`へ`{"op":"contentGc"}`を送ると、Vaultの排他区間で`R2Journal.collectGarbage()`を呼び出します。既存内部secretが必要で、既定はdry runです。headから到達できる全コミット・本文・バイナリ原本を保持し、既定24時間より古い到達不能オブジェクトだけを候補にします。実削除は`{"op":"contentGc","execute":true}`を指定します。ライブラリから直接呼ぶ場合もVaultの排他ロックを保持した状態で実行します。未完了チェックポイントのページ／カタログも保護します。実削除直前にもhead変化を検出します。履歴保持対象は回収しません。R2ライフサイクルで`objects/`や`commits/`を一律削除しないでください。

## 容量・性能と検証範囲

本文をSQLiteへ退避して容量制限を隠す方式は使いません。現存文書・競合葉・ローカル同期進捗・索引管理情報は1VaultのSQLite DOに収まる必要があります。[公式上限](https://developers.cloudflare.com/durable-objects/platform/limits/)はPaidで1DO 10GB、Freeでは1GBです。

`vaultStatus`／`indexStatus`の`capacity`は公式SQL APIの`databaseSize`、設定上限・余裕・書込可否を返します。既定は`SQLITE_MAX_BYTES=900000000`、`SQLITE_HEADROOM_BYTES=100000000`で、800MB以上ならバックグラウンド圧縮を予約し、完了前も増加する更新をHTTP 507 `SQLITE_CAPACITY`で拒否します。完了後に再試行し、改善しなければ引き続き拒否します。読取と明示圧縮は継続できます。Paidでは実プラン確認後に上限を9500000000以下へ設定でき、500000000程度の余裕を推奨します。ライブラリ埋込では`VaultBindings.sqliteMaxBytes`／`sqliteHeadroomBytes`を使用します。上限近くで巨大な1リクエストを受ける場合の実`SQLITE_FULL`・CPU制限までは完全には防ぎません。

検索は形式v2の共有転置索引で該当単語のページを読み、全ノートの索引GET／LISTを避けます。希少語・不一致語の読取は木の深さに依存しますが、共通語は該当文書数に比例し、正確なBM25統計と順位付けのため複数回走査します。無効な候補が多い場合も走査が増えます。本番の遅延・費用は未測定です。通常復旧はチェックポイント以降に限定し、本文を一括保持しません。ただし旧形式のチェックポイント未作成履歴、GCの全履歴走査、深い版のR2アーカイブ参照、明示移行には履歴量／現存メタデータ量に比例する費用が残ります。大量データでの本番適性をこのテスト結果から主張しません。

テストはローカルworkerdの本物のWorkers／DO／R2バインディングです。CPU制限による実強制終了、ネットワーク断、本番R2障害、本番負荷、大規模な本番クライアント同期は未検証です。実Obsidianと公式CLIの隔離E2Eは[テスト文書](testing.md)の通り成功しています。保存境界での注入障害、成功head後の応答喪失、管理DB消去後の再生は検証しています。

## 実DO内部のVault識別

実workerdのDO内部では`ctx.id.name`が取得できない場合があります。認証済みWorkerとVaultClientは、`X-LiveSync-Vault-Ref`へ`encodeURIComponent(JSON.stringify(ref))`、既存`X-LiveSync-Internal`へ内部secretを設定します。DOはsecret・実DO ID一致・ホストpolicyを確認して識別情報だけをDO KVへ保持します。R2ホストの識別不能は失敗として返し、本文のSQLite fallbackには入りません。初回の直接内部API／旧源移行呼出も、識別がまだ保持されていなければこの信頼済み参照が必要です。認証前の外部ヘッダーはWorkerが上書きします。

## 公平な保守と派生索引

alarmはチェックポイント1段階と索引1段階を交互に進めます。失敗したジョブだけが他方を占有しません。索引は1回最大16パス、パス間で50msを目安に延期します。1パスの処理を途中で強制中断する期限ではありません。延期は失敗回数に加算せず、pendingとして保存します。欠落チャンク到着時は再試行上限に達したノートもカーソルで全件再確認し、実際に試したパスまでだけカーソルを進めます。進行中の追加チャンク到着は次の全件走査を予約します。継続alarmが実行され、各パスの処理が有限時間で終わり、入力が収束する条件で完了します。絶えず増えるdirty更新下でチェックポイント完了時間の上限は保証しません。

索引版4への更新で再構築を開始します。既存の形式v1のactive世代は新世代完成まで検索でき、再構築中の保存失敗で切り替えません。形式v2は不変の文書木・単語／パス木とCAS更新するmanifestを持ちます。32パスまたは256KiBを目安に小変更を木へ統合し、通常の小更新は有界なmanifest deltaを使います。木の葉は64行／512KiBを目安、分岐は32、キャッシュは最大16ページです。単一ノートの巨大な投稿は512KiBを超え得て、ページJSONを一度解析します（ストリームJSON解析ではありません）。索引対象ノートの100万UTF-16単位制限とリクエスト制限が残り、本番CPU／メモリ適性の保証ではありません。

独立した不変ページPUTは最大4並列で、開始した保存の全終了を待ってから失敗を返します。writerのupsert／deleteは仮確定であり、close成功まで完了と扱いません。close失敗は試した全パス（削除を含む）を再試行します。全文検索は最大4096 UTF-8バイト／32種類の単語、ライブラリの件数は1〜1000（MCPは既存1〜50）です。解析、AND、フレーズ位置、BM25重み、原文ハイライト、フォルダ／Vault制限と原本ハッシュ検証を維持します。

派生索引の`collectGarbage`は既定dry run／24時間猶予です。直接呼出はVault writerと同じ排他ロック内で実行し、進行中の読取より十分長い猶予を設定してください。active／buildingの根・delta・原文参照と旧active世代全体を保護します。R2コンテンツ正本のGCとは別で、公開MCP操作は追加していません。現在の本番移行・回収は実行していません。
