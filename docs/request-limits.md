# リクエスト上限

上限の値は、ライブラリの `REQUEST_LIMITS`（`src/livesync/limits.ts`）で定義しています。
CouchDB 互換の設定 API が返す値と、実際の検査は同じ定数を使います。

| 対象 | 上限 | 数え方 |
|---|---:|---|
| DO への HTTP 本文、公開している POST `_changes` | 16MiB（16,777,216 bytes） | 読み取った本文の実際のバイト数 |
| LiveSync の文書、ローカル同期の文書 | 4MiB（4,194,304 bytes） | 入力オブジェクトを `JSON.stringify` して UTF-8 に符号化したサイズ |
| POST `_bulk_docs`、`_bulk_get` | 1000 件 | `docs` 配列の長さ |
| MCP の添付の原本 | 10MiB（10,485,760 bytes） | base64 をデコードした後のバイト数 |

サイズはバイト数で数え、JavaScript の文字数では数えません。
文書の上限には、ID、rev、履歴なども含めた、空白なしの JSON 表現のサイズが対象です。
HTTP 本文の上限には、空白やバルクの外側の JSON も含みます。

1 つのファイル全体の上限と、チャンク文書の上限は別のものです。
通常、LiveSync はファイルの原本を複数のチャンクに分けて同期します。

## 上限の検査方法

本文はストリームを読みながらバイト数を数え、上限を超えた時点で読み取りを中止して、HTTP 413 `request_entity_too_large` を返します。
Content-Length がない、実際より小さい、不正な値である、といった場合も、実際のバイト数の検査は省略しません。
宣言された Content-Length が上限を超えている場合は、読み取る前に拒否します。
1 バイトずつ届くような送り方でも、保持するバッファが上限を超えて増えることはありません。

`_bulk_docs` は、件数とすべての入力文書のサイズを、最初の本文の保存、SQL の更新、復元コミットよりも前に検査します。
最後の文書だけが上限を超えている場合も、先頭の文書だけが保存されることはありません。
DO を直接呼ぶ場合、旧 SQLite 方式のホスト、MCP の内部操作も、同じ HTTP 本文の上限を通ります。

設定 API は、`chttpd/max_http_request_size` に 16777216、`couchdb/max_document_size` に 4194304、独自の `livesync/max_bulk_docs` に 1000 を返します。
設定 API への PUT は互換のためだけに受け付けるもので、上限は変わりません。

## 不正なリクエスト

JSON として解析できない本文や、JSON オブジェクトでない本文（配列や `null` など）は、CouchDB と同じく HTTP 400 `bad_request` で拒否します。
空の本文は空のオブジェクトとして扱います。
パスの DB 名や文書 ID に不正なパーセントエンコード（`%ZZ` など）がある場合も 400 を返します。

`_find` と `_changes` のセレクタの `$regex` は、パターンごとに一度だけコンパイルします。
256 文字を超えるパターン、後方参照（`\1` など）を含むパターン、量指定子のついたグループの中に（入れ子の深さを問わず）さらに量指定子か選択肢があるパターン（`(a+)+`、`((a+))+`、`(a|aa)*` など）は、どの文書にも一致しないものとして扱います。
これはバックトラックが指数的に増える典型的な形を避けるための検査で、すべての重いパターンを検出するものではありません。
`a*a*a*` のように量指定子を並べたパターンは、入力の長さに対して多項式時間かかることがあります。
LiveSync 自体は `$regex` を使いません。

## 413 が返ったときの対処

検証対象の公式共有コア 0.1.35 は、既定で `batch_size=25` です。
これらの上限は、既定の小さなチャンクとバッチによる同期を妨げない値にしています。
10MiB の添付を base64 にした本文（約 13.34MiB）も、HTTP 本文の上限に収まります。
ただし、個々の JSON メタデータが大きい場合や、設定を変えている場合は超えることがあります。
文書の上限を 4MiB にしているのは、約 3.5MB の文字とバイナリが混在した文書と、約 3MB の日本語チャンクを扱えるようにするためです。

公式コアはサイズによる失敗の一部でバッチを小さくして再試行しますが、413 では失敗として終了する場合もあります。
自動の再試行で必ず解決するとは限りません。

413 が返ったときは、`batch_size` を小さくし、大きなカスタムチャンクを避けてから再送してください。
1 つの文書だけで 4MiB を超えている場合は、バッチを小さくしても解決しません。
すでに同期済みの大きな文書は読み取れますが、上限を超える入力での新しい更新は拒否します。
上限を超えたバルクは一部も保存されないので、同じ入力を分割し、現在の rev を確認してから再送できます。

これらの上限は HTTP 本文のサイズを有限にするためのもので、任意の JSON の解析、深い履歴、読み取りの応答が、本番の CPU とメモリの上限に必ず収まることを保証するものではありません。
大きな原本は、通常のチャンク同期で扱ってください。
