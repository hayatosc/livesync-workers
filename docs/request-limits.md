# リクエスト上限とクライアント互換性

上限の正本はライブラリの`REQUEST_LIMITS`（`src/livesync/limits.ts`）です。設定APIと実際の検査は同じ定数を使います。実Cloudflare資源の変更は不要です。

| 対象 | 上限 | 検査する単位 |
|---|---:|---|
| DOへのHTTP本文／公開POST `_changes` | 16MiB（16,777,216 bytes） | 読み取った本文の実バイト数 |
| LiveSync文書・ローカル同期文書 | 4MiB（4,194,304 bytes） | 入力オブジェクトの`JSON.stringify`をUTF-8へ符号化したサイズ |
| POST `_bulk_docs`／`_bulk_get` | 1000件 | `docs`配列の長さ |
| MCP添付原本 | 10MiB（10,485,760 bytes） | base64復号後のバイト数。従来値を維持 |

1MiBは1,048,576 bytesです。日本語・絵文字をJSの文字数で数えません。文書上限には入力のID・rev・履歴等のJSONも含み、空白を除いたJSON表現で検査します。HTTP本文上限には空白とバルク外側のJSONも含みます。単一ファイル全体の上限とチャンク文書の上限は別です。通常LiveSyncは原本を複数チャンクへ分割して同期します。

本文はストリームを読みながらバイト数を検査し、上限超過でHTTP 413 `request_entity_too_large`を返します。Content-Lengthが未指定・過少・不正でも実バイト数の検査を省略しません。数値の宣言が既に上限を超える場合は読取前に拒否します。増分バッファを使い、1バイトずつ到着してもチャンク参照配列を無制限に増やしません。上限を超えたストリームはcancelします。

`_bulk_docs`は件数と**全入力文書**のサイズを、最初の本文保存・SQL更新・復元コミットより前に検査します。末尾に超過文書があっても先頭だけを保存しません。直接DO呼出、既存SQLiteホスト、内部MCP操作もHTTP本文上限を通ります。公開POST `_changes`はWorker側でも無制限に`text()`／JSON解析しません。通常の成功応答は従来通りR2本文・復元コミット・head CAS確定後です。

設定APIの`chttpd/max_http_request_size`は16777216、`couchdb/max_document_size`は4194304を返します。追加の`livesync/max_bulk_docs`は1000です。以前の4GiB／50MB表示を廃止しました。設定APIへのPUTは互換shimであり、上限を引き上げません。

## クライアント設定と再送

固定検証対象の公式共有コア0.1.35は既定`batch_size=25`です。今回の上限は既定の小さなチャンク・バッチ同期を維持し、10MiB添付のbase64本文（約13.34MiB）もHTTP上限に収まります。ただし個々のJSONメタデータやカスタム設定で超過することがあります。既存の約3.5MB混在文字バイナリ文書の往復と、約3MB日本語チャンクの索引テストを維持するため、文書上限は4MiBとしました。公式Obsidian／CLIの通常7ケースを最終headで検証します。

公式コアは一部のサイズ失敗でバッチ縮小を行いますが、413の場合は失敗として終了する分岐もあります。自動再試行で必ず解決するとは扱いません。413時は`batch_size`を減らし、大きなカスタムチャンクを避けて再送してください。文書単体の4MiB超過はバッチを減らしても解消しません。既に同期した大きな文書の読取は可能ですが、同じ超過入力での新更新は拒否します。超過したバルクは部分保存されないため、同じ入力を分割し、現在revを確認して再送できます。

HTTP本文を有限にする対策であり、任意JSONの解析／深い履歴／読取レスポンスが本番の全CPU・メモリ上限に必ず収まる保証ではありません。GiB級の本文を一度に受ける方式や実CPU上限の大規模検証は今回の対象外です。大きな原本は通常のチャンク同期を使ってください。
