## 正本保存と復元

normalは20リクエスト×新文書1件、bulk-burstは4リクエスト×25件、initialは1リクエスト×128件です。短い非圧縮本文、new_edits=falseで、alarmは停止して前景保存だけを計測しました。concurrentは16件のPUTを同時に発行し、DO内の直列化を維持します。件数をまとめたコミット／head CASは以前からあり、今回新しく加えた機能とは扱いません。新規改善は本文と完全な版履歴を1不変オブジェクトにまとめることです。1バッチN文書のPUTは2N+2からN+2です。

|操作|GET 前→後|PUT 前→後|p50 ms 前→後|p95 ms 前→後|
|---|---:|---:|---:|---:|
|normal|20 → 20|80 → 60|17 → 15|19 → 18|
|bulk-burst|4 → 4|208 → 108|193 → 113|198 → 115|
|initial|1 → 1|258 → 130|952 → 528|952 → 528|
|concurrent-16|16 → 16|64 → 48|140 → 121|278 → 241|

head 429注入は両版とも既存の250ms再試行を通り、269 → 267ms。注入は計測proxyの手前なので、この失敗1回はPUT集計に含みません。DO全管理行を消した後の復元は89 → 88 GET、291 → 318msで、今回の測定では復元速度は改善していません。offline-catchupは8回の_revs_diffのみ（両版8 GET）で、実オフライン同期全体の性能測定ではありません。実CLI／GUIでは停止・再接続・削除・復元を別途検証します。

本文／journal／head CAS成功前にはACKしません。同一キーへの独立な並行head保存を追加していません。16MiBリクエスト／4MiB文書／1000件等の既存制限を維持します。保存形式v3と旧形式読取、旧版へ直接戻せない点は[運用・復元](r2-operations.md)を参照してください。

## 索引構築と公平な保守のコスト

|索引構築|PUT 前→後|構築ms 前→後|
|---|---:|---:|
|32ノート|34 → 43|126 → 156|
|128ノート|130 → 195|467 → 788|
|512ノート|514 → 884|1847 → 3785|

共有木のcopy-on-writeは読取を減らす代わりに索引構築の書込増幅を生みます。小更新は最大32パス／256KiBを目安とするmanifest deltaに集約しますが、再構築PUT数と所要時間の増加は残ります。不変ページの独立PUTを最大4並列にしていますが、CPU／全構築費用の改善は主張しません。

128ノートのcheckpoint＋索引を手動alarmで両方完了まで進めた結果、最初の索引進捗はalarm **14 → 2**、checkpoint完了は **13 → 47**、全体時間は **1469 → 1539ms**でした。索引進捗とcheckpointを交互にするため、checkpoint完了が遅れる代わりに索引が待ち続けません。通常のalarmスケジュール待ち25ms等はこの手動測定に含まず、本番完了時間へ換算できません。変更後の1索引段階は16パス／50msを目安に区切りますが、ページ統合や単一パス処理のため50msを超えるalarmはあります。

## 未測定と次の測定

実リモートR2、大規模な共通語・巨大単語位置列、更新が収束しない場合、巨大な履歴、実CPU強制終了は未測定です。本文の正本をDOへ戻して制限を隠すことはしません。単一ページの512KiBは目標で、単一ノートの投稿が超える場合はJSONを一度解析するため、入力量に比例するメモリが残ります。

実遠隔比較が必要な場合の候補は、期間限定Worker1個、SQLite DO namespace1個、正本R2と派生R2のbucket各1個に同じ合成データを入れ、リクエスト数・総byte・同一head間隔・p50／p95を記録し、終了後に削除する方法です。これには実資源作成・利用料金・認証・削除の承認が必要で、今回実行していません。現時点で料金や速度の保証は出していません。
