# チェックポイントのローカル性能測定

2026-10-06、変更前7ffc94eとバックグラウンド処理への変更後を、同一マシン・同一ハーネスで順番に実行しました。公式Vitest Workers統合のローカルworkerd／SQLite DO／R2 bindingを使い、CONTENTの各操作に**人工的な2ms待機**を加えています。本番R2の遅延・スループット・費用を測定した結果ではありません。

通常更新20、初回同期8バッチ×32文書、同時更新20、圧縮済み512版の更新10、長期オフライン復帰9リクエストを測定しました。チェックポイント境界は128／1024文書で独立5試行、4096文書で3試行です。境界を再現するためテストでseqを設定しています。索引alarmを止め、チェックポイントを明示的にdrainして応答と保守作業を分離しています。end-to-endはdrainを含みますが、実alarmの25ms待機や実ネットワーク待機は含みません。最大SQLiteは約2.4MBであり、GiB規模・本番CPU制限を検証していません。少数試行のp95は参考値です。

## 再実行

```sh
npm ci
PERF_LABEL=after npm run test:performance
```

変更前は7ffc94eの別worktreeへ、現在の`vitest.performance.config.ts`と`test/performance/sync.test.ts`だけをコピーし、同一lockfileの依存で実行します。変更前のライブラリソースは変更しません。比較時に別テスト／E2Eを並列実行しないでください。生ログは`.local/e2e/performance-evidence/*-latest.log`に保存しました。通常の`npm test`に性能試験は含めません。

## 未検証と本番測定

実Workers CPU制限、GiB規模、実R2同一key制限、数時間の連続更新、実ユーザーVaultは未測定です。本番に近い測定には、臨時Worker1個・SQLite DO namespace・CONTENT／SEARCHのR2 bucket2個、限定認証情報、Worker CPU／リクエスト・R2操作／保存の課金と削除手順への別途承認が必要です。今回これらの作成・deploy・実データ移行は実行していません。
